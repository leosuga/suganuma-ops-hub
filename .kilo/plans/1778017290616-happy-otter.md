### Detalhes técnicos — 2.5 React Compiler
A configuração no Next.js 16 seria:
```ts
const nextConfig = {
  experimental: {
    reactCompiler: true,
  },
} satisfies NextConfig
```
Requer `babel-plugin-react-compiler` ou `react-compiler-runtime`. Pode não ser trivial — **adicionar apenas se build passar sem erros.**

### Detalhes técnicos — 3.1 Realtime
O hook `useRealtimeTable` em `src/lib/realtime.ts` recebe `(table: string, queryKey)`. Basta adicionar no topo das query hooks:
```ts
export function useNotes() {
  useRealtimeTable("note", noteKeys.all)  // faltando hoje
  return useQuery({...})
}
```

## 4. Performance — TanStack Query, prefetch e imagens

| # | Tarefa | Motivo | Impacto |
|---|--------|--------|---------|
| 4.1 | **Padronizar `staleTime`/`gcTime` no TanStack Query** | Sem defaults, cada query refetcha imediatamente ao re-focus. `staleTime: 60_000` para listagens é suficiente e reduz chamadas ao Supabase. | API usage / UX |

## 6. Migração para Coolify — Plano Completo e Future-Proof

### Contexto da migração
O deploy atual funciona via SSH + Docker manual. O Coolify (`coolify.suganuma.com.br`) já está instalado no mesmo VPS. O objetivo é transferir o gerenciamento do app (e futuros apps) para o Coolify, eliminando a necessidade de GitHub Actions + SSH para deploy.

**Decisões arquiteturais já confirmadas:**
- Supabase é self-hosted no mesmo VPS
- Caddy proxy atual foi criado manualmente (não pelo Coolify)
- Coolify já está ativo em `coolify.suganuma.com.br` (porta desconhecida, provavelmente 8080 ou 8000)
- Futuros apps usarão **subdomínios** (ex: `app2.suganuma.com.br`)

---

### 6.1 Pré-requisitos e Diagnóstico

Antes de tocar em qualquer coisa:

1. **Acessar o dashboard do Coolify** em `https://coolify.suganuma.com.br` e verificar:
   - Versão do Coolify (ajuda a saber quais features estão disponíveis)
   - Se o servidor VPS já está registrado como "Server"
   - Se há projetos/apps antigos que precisam ser limpos
   - Qual proxy está configurado (Traefik ou Caddy)

2. **Backup do estado atual**:
   ```bash
   # No VPS, como root ou sudo:
   # 1. Backup do banco Supabase (se estiver em Docker)
   docker exec -it <supabase-db-container> pg_dump -U postgres -d postgres > ~/backup-supabase-$(date +%Y%m%d).sql

   # 2. Backup das variáveis de ambiente
   cp ~/ops-hub/.env.prod ~/backup-env-$(date +%Y%m%d)

   # 3. Backup do Caddyfile manual
   cp /path/to/Caddyfile ~/backup-caddy-$(date +%Y%m%d)

   # 4. Listar todos os containers e volumes
   docker ps -a > ~/backup-docker-ps-$(date +%Y%m%d).txt
   docker volume ls > ~/backup-volumes-$(date +%Y%m%d).txt
   ```

3. **Verificar se o Caddy do Coolify pode assumir o proxy**:
   - Coolify pode usar Traefik (padrão) ou Caddy como proxy
   - Se o proxy atual é Caddy manual, a migração é mais suave se mantivermos Caddy
   - Se Coolify estiver com Traefik, precisamos decidir: migrar para Caddy no Coolify ou manter Caddy manual separado

---

### 6.2 Estratégia de Proxy (decisão crítica)

**Opção A — Coolify com Caddy (recomendada para você)**
- Como você já usa Caddy manualmente, configurar o Coolify para usar Caddy como proxy interno é o caminho mais natural
- O Caddy do Coolify gerencia todos os subdomínios automaticamente via labels Docker
- Seu Caddy manual atual pode ser desativado gradualmente

**Opção B — Manter Caddy manual + Coolify com Traefik**
- Caddy manual continua gerenciando `ops.suganuma.com.br`
- Coolify/Traefik gerencia novos apps em subdomínios
- **Conflito**: dois proxies na mesma máquina disputando portas 80/443
- Requer configuração complexa de portas alternativas ou separação de IPs

**Opção C — Migrar tudo para Traefik (padrão Coolify)**
- Traefik é o proxy padrão do Coolify, mais integrado
- Requer aprender configuração de labels Traefik (diferente do Caddyfile)
- Não aproveita seu conhecimento atual de Caddy

> **Recomendação: Opção A** — Configurar Coolify para usar Caddy como proxy. Mantém sua stack familiar, unifica tudo num só proxy, e permite gerenciar subdomínios via UI do Coolify.

---

### 6.3 Passo a passo da migração

#### Fase 1 — Preparação (sem downtime)

1. **Configurar Coolify para usar Caddy como proxy** (se ainda não estiver):
   - No dashboard Coolify: Settings → Proxy → selecionar Caddy
   - Se estiver em Traefik, a mudança para Caddy pode requerir recriação de recursos

2. **Conectar o servidor VPS ao Coolify** (se ainda não estiver):
   - No Coolify: Servers → Add Server → IP do VPS + chave SSH
   - Coolify instala agentes Docker no servidor automaticamente

3. **Criar Project no Coolify**:
   - Name: `suganuma-apps`
   - Description: `Apps pessoais e familiares`

4. **Criar Environment**:
   - Production (`prod`)
   - Opcional: Staging (`staging`) para PR previews futuros

#### Fase 2 — Criar App no Coolify (teste com nova imagem)

1. **No Coolify**: Projects → `suganuma-apps` → Add Resource → Application
   - Name: `ops-hub`
   - Build Pack: `Dockerfile`
   - Git Repository: `https://github.com/leosuga/suganuma-ops-hub`
   - Branch: `main`

2. **Configurar Environment Variables** no Coolify UI:
   ```
   NEXT_PUBLIC_SUPABASE_URL=<mesmo valor>
   NEXT_PUBLIC_SUPABASE_ANON_KEY=<mesmo valor>
   SUPABASE_SERVICE_ROLE_KEY=<mesmo valor>
   WEBHOOK_SECRET=<mesmo valor>
   ```
   > Diferença crucial: no Coolify, env vars são injetadas no **runtime** (`docker run`).
   > Mas `NEXT_PUBLIC_*` precisam estar disponíveis no **build time** (`next build`).
   > Coolify v4+ suporta isso automaticamente se as variáveis estiverem definidas antes do build.

3. **Configurar Dockerfile Path**: `Dockerfile` (raiz do repo)

4. **Configurar Domain**:
   - `ops.suganuma.com.br`
   - Coolify/Caddy gerencia SSL Let's Encrypt automaticamente

5. **Health Check**:
   - Path: `/api/health` ou `/sw.js`
   - Coolify monitora e restarta se falhar

6. **Deploy inicial (teste)**:
   - Clicar "Deploy" — Coolify faz `git clone → docker build → docker run`
   - Verificar se container subiu e responde em `ops.suganuma.com.br`
   - **Não desligar o container manual ainda!**

#### Fase 3 — Validação e Cutover

1. **Testar app no Coolify**:
   - Login, navegação, tasks, finance, health, notes, meals, habits
   - Verificar se Supabase self-hosted é acessível (mesma rede Docker ou IP público)
   - Verificar se MCP Server funciona (`/api/agent/*`)
   - Verificar PWA (sw.js, manifest)

2. **Comparar containers**:
   - Container Coolify deve estar rodando na mesma rede que o Supabase (se Supabase for Docker na mesma máquina)
   - Se Supabase for acessível via `localhost:5432` ou IP interno, verificar se Coolify consegue rotear

3. **Switch de DNS (se necessário)**:
   - Se Caddy do Coolify já está na porta 80/443, ele já responde por `ops.suganuma.com.br`
   - Se Caddy manual ainda está ativo, pode haver conflito
   - Solução: parar Caddy manual (`docker stop caddy_proxy`) e deixar Coolify/Caddy assumir

4. **Desativar deploy antigo**:
   - Parar container manual: `docker stop suganuma-ops-hub`
   - Remover do auto-start: `docker rm suganuma-ops-hub`
   - Atualizar GitHub Actions para **não fazer deploy** (ou manter como fallback)

#### Fase 4 — Limpeza e Otimização

1. **Remover recursos manuais obsoletos**:
   - Container `caddy_proxy` manual (se Coolify/Caddy está funcionando)
   - Diretório `~/ops-hub` (Coolify faz clone próprio)
   - Script `~/update-ops-proxy.sh` (não mais necessário)

2. **Atualizar GitHub Actions** (opcional):
   - Manter workflow mas mudar para **trigger manual** (`workflow_dispatch`) como fallback
   - Ou remover completamente e confiar no Coolify auto-deploy

3. **Configurar auto-deploy no Coolify**:
   - GitHub App ou Webhook para deploy automático no push
   - Ou usar Deploy Key para pull-based

4. **Testar rollback**:
   - No Coolify: Deployments → escolher versão anterior → "Rollback"
   - Verificar se a app volta ao estado anterior em segundos

### 6.4 Considerações especiais

#### Supabase self-hosted
Se o Supabase está rodando em containers Docker manuais no mesmo VPS:
- **Opção A (recomendada)**: Manter Supabase fora do Coolify. Ele é infraestrutura de dados, não "app". O app no Coolify se conecta ao Supabase via IP interno ou `host.docker.internal`.
- **Opção B**: Migrar Supabase para Coolify como "Service" (Coolify tem template de Supabase). Isso dá backup automático, monitoring, etc. **Mas** requer export/import do banco e reconfiguração de URLs.

> **Recomendação: Opção A** — Supabase permanece fora do Coolify por enquanto. Menor risco, menos complexidade.

#### Futuros apps com subdomínios
Com Coolify configurado, adicionar novo app é:
1. Criar novo Resource no Project `suganuma-apps`
2. Configurar domínio: `app2.suganuma.com.br`
3. Coolify/Caddy gera SSL automaticamente
4. Deploy — app está online

Não precisa editar Caddyfile, não precisa script de proxy, não precisa SSH manual.

#### PR Previews (Deploy de branches)
Com Coolify v4+ e GitHub App configurado:
- Abrir PR no GitHub → Coolify deploya automaticamente em `pr-42.ops.suganuma.com.br`
- Merge na main → deploy automático em `ops.suganuma.com.br`
- Requer configuração de "Preview Deployments" no Coolify

### 6.5 Rollback plan (se algo der errado)

Se a migração falhar em qualquer ponto:

1. **App não sobe no Coolify**:
   - Reativar container manual: `docker run -d --name suganuma-ops-hub ...` (comando do deploy.yml)
   - Verificar logs do Coolify para erro de build
   - Corrigir e tentar novamente

2. **SSL/DNS quebrado**:
   - Se Caddy do Coolify não consegue gerar certificado, reativar Caddy manual temporariamente
   - Verificar se DNS aponta corretamente para o VPS
   - Coolify/Caddy precisa de porta 80 aberta para ACME challenge

3. **Banco inacessível**:
   - Se o app no Coolify não conecta ao Supabase, verificar:
     - Supabase container ainda roda? (`docker ps`)
     - App no Coolify está na mesma rede Docker que Supabase?
     - Ou está usando IP público/localhost corretamente?

4. **Volta completa ao estado anterior**:
   - Parar container Coolify do app
   - Subir container manual
   - Restaurar Caddy manual se necessário
   - Tudo feito em < 5 minutos se backups estiverem em ordem
